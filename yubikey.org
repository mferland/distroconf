#+title: YubiKey 5 NFC setup on Arch Linux and Omarchy

* Before enrolling the key

- Keep recovery codes and an independent way to sign in to every account.
- Where a service permits it, register at least two security keys and test both
  before removing an existing authentication method.
- Do not commit PINs, recovery codes, PAM enrollment data, SSH credential
  handles, or other key material to this repository.
- A FIDO reset deletes every FIDO2 and U2F credential on the YubiKey. Do not run
  ~ykman fido reset~ as a troubleshooting step.

The instructions below use USB for initial management and enrollment. NFC use
on a computer requires a compatible PC/SC reader and support from the
application or browser; the YubiKey's NFC capability alone is not sufficient.

* Install and inspect the key

Install the command-line manager and FIDO2 tools through Omarchy's package
helper:

#+begin_src sh
omarchy pkg add yubikey-manager libfido2
#+end_src

Insert the YubiKey over USB, then confirm that it is detected:

#+begin_src sh
ykman list
ykman info
ykman fido info
fido2-token -L
#+end_src

Set the FIDO2 PIN interactively. Do not pass the PIN as a command-line option,
because command lines can be retained in shell history and exposed to other
processes.

#+begin_src sh
ykman fido access change-pin
ykman fido access verify-pin
#+end_src

A new YubiKey has no FIDO2 PIN by default. Eight consecutive incorrect PIN
attempts lock the FIDO application and require a destructive FIDO reset, so
stop and verify the PIN instead of repeatedly guessing.

* Register the key with websites

In each service's security or multi-factor-authentication settings, add a
security key or passkey and follow the browser prompts. Register the backup
YubiKey separately, save recovery codes offline, and test both keys before
removing the previous sign-in method.

WebAuthn enrollment is service-specific and should not be automated or stored
in this repository.

* Create a hardware-backed SSH credential

Confirm that the installed OpenSSH supports security-key algorithms:

#+begin_src sh
ssh -Q key | grep '^sk-'
#+end_src

Create a resident Ed25519 credential that requires the FIDO2 PIN as well as a
touch. The command prompts for the YubiKey PIN and for a passphrase protecting
the local credential-handle file.

#+begin_src sh
ssh-keygen -t ed25519-sk -O resident -O verify-required \
  -C "$USER@$(hostname)-yubikey" \
  -f ~/.ssh/id_ed25519_sk_yubikey
#+end_src

Some older YubiKey 5 firmware does not support Ed25519 security-key
credentials. If the key reports that the algorithm is unsupported, use ECDSA:

#+begin_src sh
ssh-keygen -t ecdsa-sk -O resident -O verify-required \
  -C "$USER@$(hostname)-yubikey" \
  -f ~/.ssh/id_ecdsa_sk_yubikey
#+end_src

The private file created by ~ssh-keygen~ is a credential handle, not the private
cryptographic key itself; signing still requires the YubiKey. Treat the file as
sensitive and back it up securely. Copy the corresponding ~.pub~ file to the
Git host or server, then test it before removing any existing key:

#+begin_src sh
cat ~/.ssh/id_ed25519_sk_yubikey.pub
ssh -T git@github.com
#+end_src

Because the credential is resident, its handles can be recovered on another
computer. Run this from an empty temporary directory: ~ssh-keygen -K~ writes
the recovered handle files into the current directory.

#+begin_src sh
recovery_dir=$(mktemp -d)
cd "$recovery_dir"
ssh-keygen -K
#+end_src

Inspect the generated files, move only the intended credential into ~~/.ssh~,
and set mode ~600~ on its private handle and ~644~ on its public key.

* Use the same YubiKey on Ubuntu 22.04 at work

If you created the resident SSH credential above, you do not need another SSH
key just because you use another workstation. Recover its local handle on the
workstation; the private cryptographic key stays on the YubiKey. Existing
server registrations for that public key continue to work.

On the Ubuntu workstation, install the SSH client and check its capabilities:

#+begin_src sh
sudo apt update
sudo apt install openssh-client
ssh -V
ssh -Q key | grep '^sk-'
#+end_src

Downloading resident credentials requires OpenSSH 8.3 or newer; using
~verify-required~ requires 8.4 or newer. Connect the YubiKey by USB and use its
existing FIDO2 PIN. Run recovery in an empty directory to avoid overwriting
any existing SSH files:

#+begin_src sh
mkdir -p ~/.ssh
chmod 700 ~/.ssh
recovery_dir=$(mktemp -d)
cd "$recovery_dir"
ssh-keygen -K
ls -l
#+end_src

Recovery prompts for the PIN and writes handle and public-key files into that
directory. It can recover several credentials. Inspect the public-key
fingerprints and select the one matching the public key you registered with
your Git host or server:

#+begin_src sh
ssh-keygen -lf ./id_ed25519_sk_rk.pub
#+end_src

The recovered filename can differ, especially for ECDSA or a custom
application name. Substitute the actual filenames below. Use a destination
name that is not already in use; ~-i~ prompts before overwriting:

#+begin_src sh
mv -i ./id_ed25519_sk_rk ~/.ssh/id_ed25519_sk_yubikey
mv -i ./id_ed25519_sk_rk.pub ~/.ssh/id_ed25519_sk_yubikey.pub
chmod 600 ~/.ssh/id_ed25519_sk_yubikey
chmod 644 ~/.ssh/id_ed25519_sk_yubikey.pub
ssh-keygen -p -f ~/.ssh/id_ed25519_sk_yubikey
#+end_src

The final command sets a local passphrase on the recovered handle. Recovery
does not restore the passphrase used on the other workstation.

Test with an explicit identity; replace the destination with your work Git
host or SSH server:

#+begin_src sh
ssh -o IdentitiesOnly=yes -i ~/.ssh/id_ed25519_sk_yubikey -T git@github.com
#+end_src

For regular use, merge an entry into ~~/.ssh/config~ for the intended host:

#+begin_src conf
Host github.com
    IdentityFile ~/.ssh/id_ed25519_sk_yubikey
    IdentitiesOnly yes
#+end_src

If the original SSH credential was non-resident, ~ssh-keygen -K~ cannot
recover it. Securely transfer its existing handle file and public key from
the original machine, or create a separate credential and register its public
key with the work service.

** When to create a separate work SSH credential

A separate work credential is useful when work and personal access should be
revoked independently, or your employer requires a dedicated key. It can
live on the same YubiKey. Give it a distinct application name so it does not
replace the existing resident credential:

#+begin_src sh
ssh-keygen -t ed25519-sk -O resident -O verify-required \
  -O application=ssh:work \
  -C "work-yubikey" -f ~/.ssh/id_ed25519_sk_work
#+end_src

Use a filename and application name that are not already in use. Use
~ecdsa-sk~ instead if your hardware does not support Ed25519. Register the
new ~.pub~ file with the work service and configure its host entry to use
~IdentityFile ~/.ssh/id_ed25519_sk_work~.

Website security-key registrations already on the YubiKey can also be used
from the work browser by selecting the security-key sign-in option. A new
work account needs its own enrollment. Local sudo enrollment is separate and
must be configured on each workstation; the Arch/Omarchy package commands
and PAM changes below are not Ubuntu workstation setup instructions.

* Optional: use the key for sudo authentication

This is optional and can lock out administrative access if configured
incorrectly. Keep a root shell open, retain password authentication, and test
in a second terminal before closing the recovery shell.

Install the PAM module and create a per-user enrollment file. If that file
already exists, back it up and review it instead of overwriting it:

#+begin_src sh
omarchy pkg add pam-u2f
mkdir -p ~/.config/Yubico
chmod 700 ~/.config/Yubico
pamu2fcfg > ~/.config/Yubico/u2f_keys
chmod 600 ~/.config/Yubico/u2f_keys
#+end_src

To enroll a backup key for the same account, insert it and append its mapping:

#+begin_src sh
pamu2fcfg -n >> ~/.config/Yubico/u2f_keys
#+end_src

Back up ~/etc/pam.d/sudo~, then add the following line before its existing
~auth~ rules:

#+begin_src conf
auth sufficient pam_u2f.so cue
#+end_src

This initial policy means “YubiKey or the existing password”; it is not strict
two-factor authentication. Test both paths in another terminal:

#+begin_src sh
sudo -k
sudo true
#+end_src

Do not make ~pam_u2f~ required for sudo, login, the lock screen, or display
manager authentication until a recovery path and the exact PAM control flow
have been tested. The mapping file binds a local user, host, and hardware key,
so it remains local rather than being tracked by distroconf.

* Optional: enable smart-card applications

PIV and OpenPGP use the smart-card stack and have PINs and credentials separate
from FIDO2. Install their transport tools without initializing or resetting the
applications:

#+begin_src sh
omarchy pkg add pcsclite ccid opensc
sudo systemctl enable --now pcscd.socket
ykman piv info
ykman openpgp info
#+end_src

A PIV or OpenPGP key ceremony needs a separate plan for PINs, management keys,
certificate or subkey backups, and revocation material. Do not reset either
application merely to explore it.

* Troubleshooting

Start with non-destructive checks:

#+begin_src sh
ykman list
ykman info
ykman fido info
fido2-token -L
journalctl -b --no-pager | grep -Ei 'yubi|fido|hidraw|pcsc'
#+end_src

For PIV, OpenPGP, or an NFC reader, also inspect the smart-card service:

#+begin_src sh
systemctl status pcscd.socket
#+end_src

Reinsert the key directly into the computer rather than through a hub, try a
different USB port, and confirm that a browser or other process is not already
using it. Do not work around device-access errors by making ~hidraw~ devices
world-writable.
